## Correction to the original criterion (c)

The brief specified criterion (c) as "alpha-v Tyr178 pi-stacking
(T-shaped)". That criterion is **not satisfiable**: PLIP reports **zero**
`pi_stacks` for the deposited 8W30 structure. The cause is a centroid-cutoff
limitation, not a missing interaction -- PLIP's default pi-stack centroid
cutoff is **5.5 A**, while the measured ligand-to-Tyr178 centroid distance
in 8W30 is **6.21 A**. PLIP instead reports the Tyr178 contact as a
`hydrophobic_interaction` at 3.70 A.

This is the same centroid-cutoff failure mode that caused the v1
distance-based criterion to reject its own crystal structure and motivated
moving to PLIP in the first place. Requiring a pi-stack here would make the
gate reject the only crystallographically observed binder for this target
-- reproducing the exact error the move to PLIP was meant to fix. Criterion
(c) was therefore implemented as type-agnostic ("a Tyr178 contact is
reported in ANY interaction type") in `scripts/validate_plip.py`, and pinned
by `tests/test_validate_plip.py::test_tyr178_contact_reported_as_hydrophobic_satisfies_the_criterion`
and `::test_tyr178_contact_reported_as_hbond_also_satisfies_the_criterion`.
PLIP's published centroid cutoff was not retuned to force a pi-stack
classification -- inventing a threshold to obtain a desired classification
is the failure mode this campaign is correcting, not a fix to apply here.

## Converter control (crystal ligand, native pose, through poses_to_complex.py)

Task 11's `poses_to_complex.py` converts a docked pose plus
`docking/v2/receptor_h.pdb` into a PLIP-ready complex. An earlier review
found that a *docked* pose routed through the converter showed a different
PLIP interaction pattern (protein-donor H-bonds to Tyr133/Ser134/Leu225 at
3.81 A) than the deposited file (ligand-donor Asn224 at 2.63 A), and judged
this most consistent with genuine pose divergence -- but named a control
that was never run: take the **crystal ligand in its native pose**, route
it through the converter, run PLIP, and compare residue-by-residue against
PLIP on the deposited file. That control was run here.

Procedure: the `A1A` HETATM records for the ligand were extracted directly
from `8W30.pdb` (no coordinate change -- this is the deposited crystal
pose), passed through `poses_to_complex.build_complex()` against
`docking/v2/receptor_h.pdb` (ligand residue name becomes `LIG` through the
converter, not `A1A`), and the resulting complex was run through real PLIP.

Result, same pose, two paths:

| Interaction | Deposited 8W30.pdb (hetid A1A) | Native pose via poses_to_complex.py (hetid LIG) |
|---|---|---|
| Asn224 ligand-donor H-bond | 2.63 A, don_angle 156.61 deg, protisdon False | 2.63 A, don_angle 156.6 deg, protisdon False -- **reproduced** |
| Tyr133 H-bond | 3.17 A, protisdon True | 3.17 A, protisdon True -- **reproduced** |
| Ser134 H-bond | 3.47 A, protisdon True | 3.47 A, protisdon True -- **reproduced**, plus one extra Ser134 sidechain H-bond at 3.04 A not present in the deposited report |
| Asn224 protein-donor H-bonds | 3.23 A, 3.27 A | 3.23 A, 3.27 A -- **reproduced** |
| Tyr178 hydrophobic contact | 3.70 A | 3.70 A -- **reproduced** |
| Leu225 hydrophobic contact | 3.69 A | 3.69 A -- **reproduced** |
| MIDAS Ca-ligand coordination (2.62 A) | present, site merged as `A1A-CA` | **absent from the LIG site** -- see finding below |

**Finding (converter defect, not a pose-divergence artifact):** for the
identical crystal pose, `poses_to_complex.py`'s output does NOT reproduce
PLIP's ligand-calcium metal-complex merge. On the deposited file PLIP
merges the ligand and the adjacent MIDAS calcium into one site
(`hetid A1A`, `longname A1A-CA`), so `parse_report(hetid="A1A")` sees the
ligand's own 2.62 A calcium coordination. On the converter's output, PLIP
instead keeps the calcium as its own separate `CA`/`CA` sites (six of them,
matching the six calciums carried in `receptor_h.pdb`) and the `LIG` site's
`metal_complexes` list is empty -- selecting by hetid `LIG` never sees the
metal contact at all, even though the same calcium ion is present in the
input file. This means **any docked pose put through this converter and
then validated by criterion (a) as implemented (site selected by hetid)
will never show a MIDAS calcium coordination**, independent of whether the
pose is geometrically correct. This is a real converter/site-selection
interaction, not the pose-divergence explanation the earlier reviewer
proposed for the H-bond-pattern difference on a docked pose -- for the
*same* crystal pose, the H-bond and hydrophobic pattern is reproduced
almost exactly (one extra plausible Ser134 sidechain H-bond, likely a
protonation-state difference from Open Babel's `-h`), but the metal-complex
merge is not. Downstream tasks that apply criterion (a) to converter output
should not select by ligand hetid alone for the metal criterion; they
should also check the calcium's own site(s), or accept a metal_complexes
entry whose `resnr_lig`/`reschain_lig` matches the MIDAS calcium's known
residue number regardless of which site record carries it. This is
reported as a finding, not worked around, per instruction.

## Outcome

PLIP passes the crystal validation gate against the deposited 8W30
structure using the corrected, type-agnostic Tyr178 criterion above. PLIP
is adopted as the campaign's pose filter. The converter-merge finding above
is a real limitation of `poses_to_complex.py` + hetid-only site selection
for the metal criterion specifically, and should be accounted for wherever
criterion (a) is applied to converter-built complexes in later tasks.
